# Демо-скрипт: AIOps — устаревшие правила и непокрытое

> **Как пользоваться:** открываем `docs/mockup_l2/index.html` (локально, без сервера).
> По ходу рассказа кликаем по тем местам, что в `→ скобках`.
> Длительность: ~6-7 минут устного.

## 1. Вступление — масштаб и КАК это получилось (60 сек)

**→ Вкладка «Классы L2», смотрим на полоску статов вверху.**

«За **10 дней** реальной банковской системы из OpenRCA — Tomcat-фронт, MySQL, инфра-хосты — мы поймали **182 562** сырых алерта. Центр интеграции тут же снял **35 984 точных дубля** — это когда один и тот же инцидент прилетает из двух источников в одно окно. Осталось **146 578 уникальных** событий, и AIOps сама разложила их на **7 семантических классов** через **107 шаблонов**. Получилось **7 186 инцидентов** — серий близких по времени срабатываний одного шаблона на одном хосте.»

**→ Перейти на вкладку «Правила внешних алертов».**

«Чтобы было понятно, **что** именно мы группировали, — три уровня обработки:

**L0 — сырые события из трёх источников:**

- **Prometheus** — 7 пороговых правил по инфра-метрикам. Порог считается автоматически как **p95 за нормальный день** (`2021_03_04`). Каждое значение выше порога → одно событие L0 (с дедупом 1 событие / 5-мин окно / хост).
- **AppMonitor** — 2 правила по сервисным метрикам: SR-drop (`sr < p05 baseline`) и MRT-spike (`mrt > 1.5 × p95 baseline`).
- **Log Agent** — обрабатывает логи через `drain3` (template mining): кластеризует похожие строки, заменяя вариативные части — IP, числа, ID — на `<*>`. Никаких заранее заданных шаблонов; столько, сколько drain3 нашёл в данных.

**L1 — повторяющиеся trigger-ключи, всего 107:**

- **99 drain3-кластеров** из логов — например `# User@Host: <*> # Query_time: <*>`. drain3 нашёл их сам.
- **6 Prometheus-правил** — `prom-cpu`, `prom-load`, `prom-wio`, `prom-jvm`, `prom-cmem`, `prom-cnet`. Заведено 7, но `prom-mysql` за эти 10 дней ни разу не превысил порог.
- **2 AppMonitor-правила** — `app-mrt-spike`, `app-sr-drop`.

Из 107 L1 **только 8 предзаданы человеком** — остальные 99 родились автоматически из текста логов. В этом смысл подключения drain3: «алфавит» событий не пишут руками, его вычисляют.

**L2 — семантические классы (наша группировка поверх L1):**

- Для метрик класс жёстко зашит в правиле: `prom-jvm` → JVM, `prom-mysql` → Slow SQL.
- Для логов класс назначается **regex-эвристикой по содержимому шаблона**, первое совпадение выигрывает:
  - `GC|ParNew|CMS|Heap|Allocation Failure|JVM` → **JVM heap & GC давление**
  - `Query_time|InnoDB|User@Host` → **Slow SQL**
  - `disk|io.wait` → **Disk IO**
  - `network|timeout|tcp|socket` → **Сетевые деградации**
  - `deploy|Tomcat|Catalina|VersionLogger` → **Tomcat деплои**
  - `cpu|memory|load|MemPercent` → **CPU/Memory нагрузка**
  - всё, что не подошло → **Неизвестно / не классифицировано** (default)

Эти 7 классов — это поставляемый набор эвристик для типового банковского стека. Заказчик видит правила прямо в интерфейсе и может их менять.»

**→ Вернуться на вкладку «Классы L2».**

«Никакой ручной настройки. Подключили три коннектора, drain3 сам построил 100 шаблонов из логов, regex навесил L2 — и через 3 минуты получили эту картину.»

## 2. Кто шумит — и почему «больше всех» ≠ «важнее всех» (40 сек)

**→ Указать на колонки L0, AutoR%, TTL мин.**

«Сверху по объёму:

- **JVM heap & GC давление** — 80k событий, 48 шаблонов, **TTL 21 минута** — это реальные проблемы, инциденты живут долго
- **Slow SQL queries** — 43k событий, TTL 10 мин — тоже не шум, по запросам кто-то реально разбирается
- **Неизвестно / не классифицировано** — 14k событий, **AutoR 66%, TTL 36 минут** — об этом отдельно, это самый интересный класс
- **Сетевые деградации** — 4k, AutoR 97%, TTL 4.6 мин — почти всё гаснет само
- **Disk IO нагрузка** — 3k, AutoR 91%, TTL 10 мин
- **Tomcat деплои** — 1.3k, **AutoR 100%, TTL 0.1 мин** — это плановые рестарты, не алерты
- **CPU/Memory нагрузка** — 1k, **AutoR 99%, TTL 0.9 мин** — короткие фоновые скачки

Ключевая мысль: **объём не равен ценности**. Правило, бьющее каждый день и гаснущее за минуту без вмешательства, — это не сигнал, это фоновый радиошум. И наоборот — небольшой класс с длинным TTL может оказаться самым важным.»

## 3. Главный инсайт №1 — устаревших правил всего пять (40 сек)

**→ Включить чекбокс «⚠ Только устаревшие» в фильтр-баре.**

«Смотрите, что осталось. AIOps применила три критерия к каждому из 107 шаблонов:

- **AutoResolve ≥ 90%** — почти всё гаснет само
- **Активность ≥ 8 из 10 дней** — бьёт хронически
- **TTL < 10 минут** — никто не успевает отреагировать

Этим трём условиям одновременно удовлетворяют **5 правил из 107**. Это и есть план на спринт — не разбираться со ста семью алертами, а починить пять источников.

Вот они:

1. `app-mrt-spike` (AppMonitor) — 2 173 события, 11 хостов, AutoR 98%, TTL 3.2 мин
2. `app-sr-drop` (AppMonitor) — 1 778 событий, AutoR 94%, TTL 7.7 мин
3. `log-tpl-83` (Slow SQL `Query_time`) — 1 524 события, AutoR 95%, TTL 2.1 мин
4. `log-tpl-87` (Slow SQL `Query_time`) — 589 событий, AutoR 100%, TTL 0.6 мин
5. `prom-load` (Prometheus load average) — 339 событий, 14 хостов, AutoR 98%, TTL 2.4 мин

Все пять — про один и тот же сценарий: порог снят с baseline-дня, baseline устарел, правило теперь срабатывает на обычной фоновой нагрузке.»

**→ Выключить фильтр обратно.**

## 4. Трейсим конкретный инцидент — `app-mrt-spike` (90 сек)

**→ Развернуть класс «Сетевые деградации» (клик по строке). Найти строку с триггером `app-mrt-spike` (Service response time spike). Кликнуть — открывается модалка.**

«Берём самый громкий из stale-правил — **app-mrt-spike** от AppMonitor, **2 173 события** за 10 дней. Что это?

**Path-цепочка наверху модалки — как этот алерт прошёл через систему:**

- **L0**: сырое событие `Service response time spike on ServiceTest3 — mrt=412ms > p95_baseline=310ms`
- **Источник**: AppMonitor, правило `app-mrt-spike` — порог равен 1.5 × p95 baseline-дня
- **L2-класс**: «Сетевые деградации» — потому что в L1-шаблоне есть слово `spike` и регекс относит его к сети

Под path-цепочкой — **жёлтый stale-баннер с приговором**:

> ⚠ Устаревшее правило — бьёт **10/10 дней**, **98% auto-resolve**, **TTL 3.2 минуты**. Рекомендация: поднять порог в источнике или добавить duration.

Что произошло: baseline был снят с конкретного дня, и кто-то забыл его пересчитать. За три недели нагрузка на сервис подросла, p95 уехал — и теперь любой обычный пик отрабатывает как инцидент.

**→ Указать на таблицу «Инциденты» внизу модалки.**

Топ-инциденты этого правила — по 11 сервисам. Зелёная галочка — auto-resolved, красный крест — кто-то трогал. **Почти всё зелёное** — это и есть подтверждение шума.

**Что делать в источнике AppMonitor:**

1. Либо пересчитать `p95_baseline` (быстро, но устареет снова)
2. Либо добавить `for: 5m` в правиле — пусть spike живёт хотя бы 5 минут, прежде чем поднимать тикет

Эта одна правка убирает **2 173 ложных события** за 10 дней.»

## 5. Cross-L2 — корреляция симптом vs корень (50 сек)

**→ Закрыть модалку. В таблице L2 развернуть «Slow SQL queries», в drill-таблице найти `log-tpl-83` (Query_time). Указать на бейдж Cross-L2.**

«Cross-L2 показывает, что инциденты одного класса часто случаются на тех же хостах в те же дни, что и инциденты другого. Это автоматически подсвечивает связки симптом-корень.

Пример: `log-tpl-83` — это шаблон Slow SQL с медленными запросами. Cross-L2 говорит: **1 524 пересечения с Disk IO и 1 082 — с CPU/Memory**. Каждое срабатывание этого шаблона совпадает по времени и хосту с алертом по диску или CPU.

**Интерпретация:** Slow SQL — это не корень, это симптом. Корень — перегруженный диск, на котором сидит MySQL. Если бы дежурный начал тюнить запросы — потерял бы день. AIOps сразу подсказывает: смотри в дисковую подсистему хоста.

**→ Развернуть класс «Неизвестно / не классифицировано», найти `log-tpl-6`.**

Ещё интереснее — `log-tpl-6` из класса «Неизвестно»: **11 684 пересечения с JVM heap, 11 669 с Disk IO**. То есть весь его объём (11 684 события) случается в те же моменты, что и JVM-алерты. Это **независимое доказательство**, что log-tpl-6 — это **тоже про JVM**, просто наша эвристика его не распознала. Перейдём к этому в следующем разделе.»

## 6. Главный инсайт №2 — класс «Неизвестно» как roadmap (90 сек)

**→ Класс «Неизвестно / не классифицировано» уже развёрнут. Указать на профиль класса.**

«Этот класс особенный — это не «реальная» категория, а **технический бакет**: «всё, что не сматчилось ни под одну из шести семантических эвристик». Зелёный блок наверху так и говорит: «default L2, ключевых слов нет».

**Цифры этого класса резко выделяются:**

- **AutoR 66%** — самый низкий из всех (у других 89-100%). Треть инцидентов кто-то трогал.
- **TTL 36 минут** — самый высокий из всех (у других 0.1-21 мин). Инциденты живут долго.
- **Всего 73 инцидента из 13 816 событий** — очень плотные серии (по ~190 событий каждая).

Это значит, что в «Неизвестно» сидят не короткие шумовые всплески, а **реальные длинные проблемы**, которые мы просто не научились распознавать.

**→ Кликнуть на верхнюю строку — `log-tpl-6`.**

Открываем модалку. Path-цепочка:

- **L1-шаблон**: `<*> <*> <*> secs] [Times: <*> sys=0.00, <*> secs]`
- **L0-пример**: `3748791.423: [CMS-concurrent-preclean: 0.016/0.016 secs] [Times: user=0.02 sys=0.00, real=0.01 secs]`
- **L2**: «Неизвестно» — потому что в L1 не осталось ключевых слов

**Видна суть проблемы:** в исходной строке есть `CMS-concurrent-preclean` — это GC-фаза. Но drain3 при кластеризации заметил, что это слово на этой позиции **меняется** между разными лог-сообщениями (`CMS-concurrent-preclean`, `CMS-concurrent-mark`, `CMS-concurrent-reset`...) и обобщил его в `<*>`. После этого regex `GC|CMS|Heap|JVM` искать в шаблоне больше нечего — слова исчезли в обобщении.

**→ Список инцидентов внизу модалки.**

Смотрим инциденты — **5 955 событий за 10 часов на Tomcat01, не auto-resolved**. **5 714 на Tomcat02, тоже 10 часов, тоже не auto-resolved**. Это не короткий шум, это **многочасовые периоды активного GC** на двух Tomcat-хостах.

**Что делать?** Два пути:

1. **Расширить regex** — добавить `concurrent-(preclean|mark|reset|sweep)` или просто `secs.*Times.*real` в JVM-словарь. Следующий запуск автоматически перетянет 11 684 события из «Неизвестно» в JVM. Один pull request на 5 минут.
2. **Использовать Cross-L2 как подсказку** — мы уже видели, что 100% этих событий пересекаются с JVM heap. Это технически подтверждает: их можно автоматически связать с JVM, даже не дописывая regex.

**Главный смысл:** класс «Неизвестно» — это **roadmap расширения системы**. Заказчик периодически смотрит в этот класс, видит топ-шаблонов, дописывает 1-2 строки в словарь — и покрытие растёт. Это **итеративный процесс, и он прозрачен**.»

## 7. Хост-уровень — где конкретно болит (40 сек)

**→ Перейти на вкладку «Хосты». Раскрыть Tomcat02 (топ строка).**

«Tomcat02 — **48 280 событий, 739 инцидентов**, почти вдвое больше второго по шуму. При этом по другим хостам всё спокойно.

В развёртке видно расклад этого хоста по L2-классам:

- В JVM heap у Tomcat02 — больше 20 шаблонов Drain3, тысячи событий
- В классе «Неизвестно» — те самые `log-tpl-6/15/5` с многочасовыми GC-инцидентами
- В CPU/Memory сидит `prom-load` с флагом ⚠ — устаревший порог

**Вывод по хосту:** проблема не системная — проблема в одном узле. Поднимать общий порог для всего кластера нельзя, мы пропустим реальные алерты на других хостах. Нужен **per-host override** для Tomcat02 — отдельный порог только для него, а ещё лучше — разобраться, почему именно этот узел делает столько GC.

Это конкретное действие админу, не «разобраться с шумом», а «вот этот хост, вот это правило, поднять порог в 1.5×».»

## 8. Финал — что мы только что сделали за 6 минут (30 сек)

«Без единого ручного запроса в Prometheus мы:

1. **Свели 182 тысячи алертов** к семи классам и 107 шаблонам — автоматически
2. **Нашли пять устаревших правил**, которые дают весь хронический шум, — система сама их пометила
3. **Прошли по конкретному инциденту от L0 до рекомендации** — где правило, что в нём не так, что чинить
4. **Связали Slow SQL ↔ Disk IO** через Cross-L2 — симптом и корень развязаны автоматически
5. **Нашли 11 684 GC-события в классе «Неизвестно»** — дефект эвристики виден, починка очевидна
6. **Локализовали Tomcat02** как источник перекоса — фикс точечный

В цифрах: эти 5 stale-правил за 10 дней дали **~6 400 ложных авто-резолв**. Одна неделя работы — пересчёт двух baseline в AppMonitor, `for: 5m` на трёх правилах, per-host override для Tomcat02 — убирает их.

Плюс **класс «Неизвестно» — это явный roadmap покрытия**: дописал regex → следующий запуск передвинул 11 684 события в JVM → класс «Неизвестно» сжался → видно следующие непокрытые паттерны. Итеративно.

И самое главное: подключили **те же три источника** на боевом контуре — получили **тот же отчёт через 3 минуты**. Это не разработка под клиента, это коробочный анализ.»

## 1. Цель

Расширить существующий L2-classes mockup (`docs/mockup_l2/index.html`):
- Визуализации (Burst, Days, EV/host) — чтобы видеть паттерны шума
- **Path инцидента** (L0 → L1 → L2) — чтобы было видно, как система классифицирует алерты
- **Флаг устаревших правил** — чтобы демонстрировать actionable инсайт
- **Объяснение классификации** — чтобы заказчик понимал, что L2 делает система сама, но честно показывает эвристики

## 2. Продуктовая модель (что мы показываем заказчику)

**L2-классификация — pre-shipped набор эвристик.** Система поставляется с готовыми паттернами, покрывающими типовые кейсы. Заказчику не надо писать L2-правила — он просто подключает свои источники алертов (Prometheus, Log Agent, AppMonitor), и система сама раскладывает события по классам.

Паттерны — это простые regex-эвристики по содержимому L1-шаблона:
- `GC|Heap|JVM|ParNew|CMS|Allocation Failure` → "JVM heap & GC давление"
- `Query_time|User@Host|Lock_time|InnoDB` → "Slow SQL queries"
- `deploy|Tomcat|Catalina|VersionLogger` → "Tomcat деплои и рестарты"
- `disk |io.wait|disk space` → "Disk IO нагрузка"
- `network|timeout|connection|tcp|socket` → "Сетевые деградации"
- `cpu|memory|load |MemPercent` → "CPU/Memory нагрузка (прочее)"
- **всё остальное** → "Неизвестно / прочее"

Демо честно показывает эти паттерны в drill-down, чтобы заказчик видел: «система не гадает, она применяет правила — и вот по каким».

Заказчик может докинуть свои L2-правила, если у него есть специфичные классы. Но для демо это опционально — работаем с коробкой.

## 3. Архитектура

### 3.1 Pipeline генерации

```
Bank/telemetry/{day}/ (10 days)
    ├── metric_container.csv  → Prometheus p95 thresholds
    ├── metric_app.csv        → SR drop + MRT spike alerts
    ├── log_service.csv       → Drain3 template mining
    └── trace_span.csv        → (not used)
        │
        ▼
[ sandbox/compute_l2_enhanced.py ] ← расширение существующего spike/mockup_l2_tables.py
        │
        ▼
[ docs/mockup_l2/index.html ] ← standalone single-file HTML (inline DATA + SVG)
```

- Скрипт кладётся в `sandbox/` — это исследовательский код для демо
- HTML остаётся в `docs/mockup_l2/` — это документ для демо

### 3.2 Формат JSON-данных

К текущим агрегатам добавляются массивы:

```typescript
interface L1TemplateEnhanced {
  // ... существующие поля (Events, Hosts, Incidents, ...)

  // Новые (считаются из сырых данных):
  burst_5min: number[]          // events per 5-min window (за все дни)
  burst_window_labels: string[] // метки окон для оси X (datetime)
  day_counts: number[]          // events per day (длина = 10)
  day_labels: string[]          // метки дней

  host_ev: { [hostname: string]: number }  // распределение по хостам

  // L2 classification metadata
  l2_keywords_matched: string[] // какие ключевые слова сматчились для отнесения к L2
  source_rule_id: string        // ID правила источника (prom-cpu, app-sr-drop, log-tpl-N)
  rule_type: string             // "metric_threshold" | "app_monitor" | "drain3_cluster"

  // Cross-L2
  related_l2: { [l2_class: string]: number }  // сколько инцидентов пересекается с другим L2
  total_incidents: number
}
```

### 3.3 Переименование класса

Текущий "Кратковременные ресурсные всплески" → **"CPU/Memory нагрузка (прочее)"**. Старое название вводит в заблуждение — туда попадают не только кратковременные всплески, но и хронический шум по CPU/memory. Новое название честно отражает содержимое.

## 4. Визуализации (inline SVG)

**Техническая заметка:** Массивы `burst_5min`, `day_counts`, `host_ev` вычисляются на этапе группировки L0→L1. Это не пост-процесс, а часть основного цикла агрегации.

### 4.1 Burst-профиль (sparkline)

Показывается при раскрытии L2-класса (drill-down), в блоке «Профиль» над вложенной таблицей L1.

- **Тип:** inline SVG polyline
- **Расположение:** внутри `<td colspan="...">` — сначала блок «Профиль» (3 SVG + подписи, ~120px), затем таблица L1
- **Данные:** массив `burst_5min` для каждого L1
- **Назначение:** видеть равномерный шум (плоская линия) vs. аномальные всплески (пики)
- **Маркировка:** если `Burstiness P95/med > 2.0` — sparkline с оранжевым контуром
- **Подпись:** «Burst P95/med = X.X — пики есть» / «— равномерно»

### 4.2 Days profile (bar chart)

- **Тип:** inline SVG bar (10 столбиков, по одному на день)
- **Данные:** массив `day_counts`
- **Назначение:** видеть mute-дни (0 событий), активные дни, перекос
- **Подпись:** «Активен X/Y дней. Пропуски: даты без событий»

### 4.3 EV/host distribution (horizontal bar chart)

- **Тип:** inline SVG horizontal bars
- **Данные:** `host_ev` — events per host
- **Назначение:** видеть перекос — один хост шумит значительно больше других
- **Метрика «скоса»:** если max(`host_ev`) > 2× median(`host_ev`) — маркер «Сильный перекос на hostX»
- **Подпись:** «max/min = X / Y, коэффициент перекоса = Z»

### 4.4 Хост-таймлайн (sparkline)

При раскрытии хоста во вкладке «Хосты»:
- **Тип:** inline SVG sparkline
- **Данные:** counts per day для данного хоста (по всем L1)
- **Назначение:** видеть, в какие дни хост был активен, с какой интенсивностью

## 5. Path инцидента и объяснение классификации

### 5.1 Блок «Как мы классифицировали» (в drill-down L2)

При раскрытии L2-класса — над графиками/таблицей блок **«Как AIOps определила этот класс»**:

```
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
  JVM heap & GC давление
  ─────────────────────────────────
  Ключевые слова, по которым мы это определили:
  GC, ParNew, CMS, Heap, Allocation Failure, JVM

  Источники, попавшие в этот класс:
  ⦿ Log Agent — 15 drain3-шаблонов (GC-логи)
  ⦿ Prometheus — 1 правило: prom-jvm (JVM Memory > p95 baseline)

  Пересечения с другими L2: 2 класса
  ▶ 58% инцидентов пересекаются с "Сетевые деградации"
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

Для класса "CPU/Memory нагрузка (прочее)" — честно пишем: «Default L2: события, не подошедшие под более специфичные паттерны.»

### 5.2 Блок «Путь инцидента» (в модалке L1)

При клике на L1-шаблон — модалка с цепочкой:

**L0-событие**: `[16:00:00] Disk IO wait above threshold on IG01: CPUWio=2.80 > p95_baseline=2.51`
↓ **Источник**: Prometheus, правило `prom-wio`
↓ **L1-шаблон**: "Disk IO wait above threshold on {host}"
↓ **L2-класс**: "Disk IO нагрузка" (матчинг по `disk |io.wait`)
↓ **Статус**: AutoResolve 94.6% — 352 инцидента, 7 мин средний TTL
↓ **Вердикт**: «Правило бьёт 10/10 дней, auto-resolve почти всегда — порог устарел»

### 5.3 Флаг «Устаревшее правило»

Правило считается устаревшим, если одновременно:
- `AutoResolve % ≥ 90` (инциденты тушатся сами)
- `Дней активности ≥ 8 из 10` (бьёт почти каждый день)
- `TTL < 10 мин` (живёт недолго — никто не успевает отреагировать)

Визуально: бейдж `⚠ Устарело` в строке L1/L2, при наведении — «Бьёт X/Y дней, 95% auto-resolve. Рекомендация: поднять порог в источнике или добавить duration.»

### 5.4 Cross-L2 корреляция

Новая колонка в таблице L2:
- Если `related_l2` не пуст — бейдж `+N пересечений`
- Клик — popover со списком: «57% инцидентов Network пересекаются с JVM heap — паттерн 'нагрузка → GC → latency'»
- В модалке L1 — аналогично

## 6. Drill-down хостов

Клик по строке хоста во вкладке «Хосты» раскрывает:
- **Таймлайн инцидентов хоста** по дням (SVG sparkline)
- **Топ L1-шаблонов** этого хоста: template, events, incidents, rule, источник
- **Флаг устаревших правил** для каждого L1 (см. 5.3)
- **Ссылка на L2-классы**: клик по L2 → таб «Классы», скролл к нужному классу

## 7. UX-детали

### 7.1 Тултипы

Иконка `ⓘ` в заголовках колонок → кастомный popover (не native title):

- **Burstiness P95/med:** «P95 / median количества событий в 5-мин окнах. Если > 2.0 — есть аномальные всплески. Если ~1.0 — равномерный шум.»
- **Events/host:** «Событий на хост = total_events / unique_hosts. Высокое значение (1000+) при малом числе хостов — правило бьёт избыточно.»
- **Days active ratio:** «Доля дней, в которые были события. Если < 0.5 — проблема эпизодическая.»
- **Dedup ratio:** «events / unique(host + 5min). Высокое значение (> 10) — плохая дедупликация.»
- **AutoResolve %:** «Доля инцидентов, закрывшихся автоматически. 90%+ при низком TTL — явный шум.»
- **TTL (среднее время жизни):** «Среднее время жизни инцидента. < 5 мин при AutoR ≥ 95% — почти всегда ложное срабатывание.»

### 7.2 Кликабельные source-чипы

- Чипы `Prometheus`, `AppMonitor`, `Log Agent` — ссылки на таб «Правила внешних алертов» с якорем на соответствующую секцию
- Вкладка «Правила» переименована в «Правила внешних алертов»

### 7.3 Фильтры

- Текущие чекбоксы CRITICAL / WARNING / INFO
- Чекбокс «Только устаревшие» (правила с флагом ⚠)
- Чекбокс «Только шумные» (AutoR ≥ 90% + TTL < 10 мин)

## 10. Демо-сценарий (памятка для рассказывающего)

Последовательность:

1. **«Вот как работает AIOps»** — начинаем с вкладки «Правила внешних алертов». Объясняем: «Система принимает алерты от Prometheus (пороги p95), AppMonitor (SR/MRT), Log Agent (Drain3-кластеризация). Это внешние правила — мы их не меняем, мы их анализируем.»

2. **«Классы проблем — наша классификация»** — переходим на вкладку «Классы». Топ-3: JVM (60k), CPU/Memory (14k), SQL (7k). Сразу видно, что JVM — главный источник шума. Показываем блок «Как мы классифицировали» для JVM: «Матчим по словам GC, Heap, ParNew — система делает это сама.»

3. **Раскрываем JVM** — графики:
   - Burst flat → нет всплесков, это хронический шум
   - Days 10/10 → правило бьёт каждый день
   - EV/host: Tomcat02 = 40k из 60k → перекос

4. **Инсайт**: «Правило prom-jvm устарело — бьёт 10/10 дней, 87% auto-resolve, Tomcat02 даёт перекос 7x. Нужен per-host override для Tomcat02 или поднять общий порог в 2×.»
   Показываем бейдж `⚠ Устарело` на L1/Prometheus-строке.

5. **Host drill → Tomcat02** — видим таймлайн инцидентов, флаг устаревшего prom-jvm, топ L1-шаблонов.

6. **Cross-L2 на Network** — «58% инцидентов Network пересекаются с JVM. Корень не в сети, а в GC-паузах под нагрузкой.»

Суть рассказа: **«Система классифицирует алерты сама, честно показывает как, и подсвечивает проблемные правила, которые надо чинить в источнике.»**

## 11. Принципы реализации

- **SVG меньше 200 байт каждая** — полилайны через `points=""`, бары через сырые `<rect>`
- **Никаких новых зависимостей** — страница грузится из одного HTML, открывается file://
- **Цветовая схема** — indigo #4f46e5 для primary, красный/жёлтый/синий для severity
- **Rus-friendly** — все подписи, тултипы, лейблы на русском (кроме кода переменных)
